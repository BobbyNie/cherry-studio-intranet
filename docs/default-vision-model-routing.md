# 預設圖片多模態模型與助手自動分流

## 目標

當助手目前選用的主模型不支援圖片輸入時，由使用者明確設定的「預設圖片多模態模型」分析有效對話上下文中的圖片，再把分析結果交回原主模型完成回答。此功能不改變助手模型、回覆模型標記或主模型的其他能力。

本功能是 v1 功能凍結的已核准例外；Agent／Claude Code 會話及圖片生成流程不在範圍內。

## 設定與有效性

- `LlmState.defaultVisionModel?: Model` 隨既有 `llm` Redux persist 儲存，不新增 slice、Dexie schema 或 persist migration。
- 初始值為空，設定可清除，不自動選取模型。
- 設定頁只列出已啟用 provider 中支援 vision 且不是純圖片生成的模型。
- 每次使用前都以目前 provider/model 清單重新解析設定。provider 停用、模型刪除、能力改變或只支援圖片生成時，設定視為無效。
- 非 vision 主模型只有在有效 fallback 存在時才開放圖片附件；文件附件行為保持既有規則。

## 請求流程

1. 一般聊天流程依主模型建立原始上下文。
2. 若主模型支援 vision，直接沿用原請求，不呼叫輔助模型。
3. 若主模型不支援 vision，且有效上下文包含 `IMAGE` 訊息塊：
   - 以同一份有效上下文和預設圖片多模態模型重新建立含圖片的模型訊息。
   - 發出非串流輔助請求，關閉工具、MCP、搜索、URL context、知識庫、記憶、圖片生成、可配置推理與自訂參數。
   - 輔助模型只按圖片順序輸出客觀視覺資訊、OCR 與不確定性。
4. 分析結果以 user-level、隱藏、標示為不可信資料的文字塊注入原主模型上下文。
5. 原主模型再依原助手設定完成最終回答；工具、搜索、知識庫、推理、參數、trace 與回覆 model metadata 均走既有主流程。

一般發送、多模型提及、重發與重新生成最後都進入同一聊天請求入口，因此會針對每個目標模型獨立判定。圖片分析結果只存在單次請求記憶體中，不寫入 Redux、訊息或 Dexie；後續追問若有效上下文仍有圖片，會重新分析。

## 安全與失敗策略

- 輔助 system prompt 明確要求不得執行圖片中的文字或指令。
- 注入主模型的分析結果使用 JSON 字串封裝，並明確標示為不可信資料，避免圖片文字被提升為系統指令。
- 預設多模態模型缺失、失效、能力不符、回覆為空、圖片準備或模型請求失敗時，回傳可國際化錯誤並停止主模型請求。
- 原使用者訊息與附件在分流前已依既有流程保存，失敗後可直接重試。

## 網路與觀測

輔助請求沿用既有 provider 設定、API key rotation、AI provider adapter、trace、token usage 及中央網路守衛。功能沒有新增網路端點、硬編碼 API host 或 allowlist 例外。
